SecondSwipe unter der Haube

Version 0.1 · Pilot · Stand 2025

Überblick

Ein Bayes'sches Empfehlungsmodell in einer Request

Der Kern von SecondSwipe ist bewusst klein: ein logistisches Regressionsmodell mit Bayes-Posterior, das pro Nutzer existiert und nach jedem Wisch in einer einzelnen Request neu trainiert wird. Keine GPU, keine Datenpipeline, kein Backend-Worker – das Modell fährt direkt im Request-Handler hoch.

TypeScript Node.js / Express SQLite React + Vite Thompson Sampling
Modell

1. Logistische Regression, Bayes'sch geregelt

Jedes Angebot wird auf ein Merkmalsvektor-Set abgebildet: Kategorie, Ära, Material, Farbe, Preisband. Die Like-Wahrscheinlichkeit ist eine Sigmoid über der Linearkombination der Gewichte: 

p(like = 1 | x, w) = 1 / (1 + exp(-w · x))

Statt eines einzelnen Schätzwerts w halten wir eine Verteilung über Gewichte. Wir starten mit einer breiten Prior-Normalverteilung und schlagen nach jedem Wisch den Posterior über die analytische Laplace-Approximation (Gauß-Posterior um das MAP) auf. Dadurch bekommen wir kostenlos eine Kovarianzmatrix und damit Unsicherheitsmasse pro Vorhersage. 

Posterior(w | D) ≈ N( w_MAP, H^-1 )

mit w_MAP als argmax der log-Posterior-Dichte und H als negativer Hesse-Matrix – beide in einem einzelnen Optimierungsschritt aus den bisherigen Wischern.

Exploration

2. Thompson Sampling statt handgetunter Regler

Für die Kartenauswahl zeichnen wir pro Kandidat einen Gewichtsvektor aus dem Posterior, bewerten die Karte damit und wählen die höchste gezogene Like-Wahrscheinlichkeit. Karten mit breitem Posterior werden häufiger gezogen und damit öfter explorert – Exploration und Exploitation entstehen automatisch, ohne einen einzigen ε- oder Temperatur-Parameter. 

for candidate in catalog:
    w ~ N(w_MAP, H^-1)      // draw sample per candidate
    score = sigmoid(w · x)
pick argmax(score)

Ergebnis: Bei wenigen Wischern ist der Posterior breit, das Modell verhält sich nahezu zufällig und erkundet den Katalog. Mit jedem Wisch schrumpft die Unsicherheit und das Sampling nähert sich der reinen Ausbeutung an.

Dwell-Time

2b. Ambivalenz messen: die Verweildauer als Signal

Nicht nur was gewischt wird, ist eine Information – auch wie lange eine Karte betrachtet wurde, bevor sie weggewischt wird. Die Dauer zwischen „Karte angezeigt" und „Wisch" ist ein beobachtbares, binär-freies Verhaltenssignal. 

// Client: misst und übermittelt die Verweildauer
const t0 = performance.now()
card.onSwipe(dir => api.post('/api/swipe', {
  cardId, dir,
  dwellMs: Math.round(performance.now() - t0)
}))

Wie daraus ein Feature wird

Die Verweildauer wird pro Wisch als Zusatzmerkmal abgelegt. Sie dient als weiche Signalkomponente, nicht als harter Label-Ersatz:

  • Ambivalenz-Indikator: Eine lange Verweildauer bei einem Like deutet auf Zögern und Relevanz hin; eine sehr kurze Verweildauer bei einem Like eher auf Impuls. Das geht als gewichtetes Zusatzmerkmal in den Posterior ein.
  • „Ähnliches zeigen": Liegt die Verweildauer über einem Schwellwert (z. B. p95 pro Sitzung), wird die Kategorie/Kandidatengruppe dieser Karte im aktuellen Stapel hochgewichtet – der Nutzer bekommt mehr Stücke, die dem zögerlich betrachteten ähneln.

Signalqualität & Ehrlichkeit

dwell(w) = softplus( (dwellMs - baseline) / scale )
score = sigmoid(w·x) · (1 + λ · similarity(dwellCard, candidate))

Verweildauer ist ein schwaches, lautes Signal. Sie wird durch Ablenkung, Ladepausen oder „drüber nachdenken ohne Interesse" verfälscht. Deshalb wirkt sie nur als weiche Gewichtung, nie als Ersatz für den Wisch-Label. Der Faktor λ ist klein und gedeckelt, damit ein Zögern das Modell nicht übersteuert.

Unsicherheit

3. Unsicherheit, die man ernst nimmt

Aus der Kovarianzmatrix berechnen wir per propagierter Unsicherheit ein 95%-Intervall für jede Like-Wahrscheinlichkeit. Entscheidend ist die ehrliche Darstellung: Nach acht Wischern ist das Intervall sehr breit (z. B. 40–97%), nicht künstlich eng. Erst mit genügend Daten nähert es sich einem präzisen Wert an. 

var = (∂p/∂w)ᵀ H⁻¹ (∂p/∂w)
ci95 = p ± 1.96 · sqrt(var)

Die Kalibrierung wird gemessen, nicht behauptet: Kalibrierungskurve und Konfusionsmatrix vergleichen die ausgewiesenen Intervalle mit den tatsächlich beobachteten Likes. Solange zu wenige Wischer vorliegen, weist die UI das Modell selbst als "unsicher" aus.

Cold-Start ehrlich behandeln. Mit 8 binären Samples ist jede Punktschätzung ein Zufallstreffer. SecondSwipe blendet das nicht aus – es zeigt das breite Intervall, damit Nutzer und Betreiber sehen, wo das Modell gerade steht.
Architektur

4. Eine kleine Cloud-Maschine, eine Request

Browser (React/Vite)
    │  HTTP
    ▼
Express (Node.js)
    ├─ /api/recommend   → Modell laden/trainieren, Thompson-Sample, Top-K zurück
    ├─ /api/swipe       → Wisch speichern, Posterior aktualisieren
    ├─ /api/profile     → Gewichte, Kalibrierung, Reset
    └─ SQLite (per-User Modelle & Wischer)

Jeder Nutzer hat ein eigenes Modell, das nur auf den eigenen Wischern trainiert wird – keine geteilten Nutzerdaten, keine Tracker. Das Modell wird pro Request aus den SQLite-Zeilen des Nutzers aufgebaut; bei Pilot-Größe (wenige tausend Wischer pro Nutzer) ist das in Millisekunden machbar.

Request-Ablauf für eine Empfehlung

GET /api/recommend
1. Wischer des Nutzers laden (SQLite)
2. Laplace-Approximation → w_MAP, H⁻¹
3. Kandidaten aus Katalog ziehen
4. Pro Kandidat: Gewichtssample, Sigmoid, Score
5. Intervall berechnen, Metadaten anreichern
6. Top-K zurückgeben
Kontrollfunktionen

5. Zurücksetzen, Rewind, keine Datenreste

Alle Steuerung ist auf Datenebene simpel und robust:

  • Rewind: Der letzte Wisch wird aus den Trainingszeilen entfernt und der Posterior auf dem reduzierten Datensatz neu gefittet – das Modell "vergisst" den Ausrutscher tatsächlich.
  • Reset: Alle Wischer und das gelernte Modell werden gelöscht; der Nutzer startet mit frischem Prior.
  • 0 Tracker: Es gibt keine serverseitige Cross-User-Verknüpfung; jede Vorhersage lebt im Request-Scope.

Grenzen

7. Was es nicht kann (noch)

  • Kalter Start ohne Nutzerdaten: Erstes Profiling ist nahezu Zufall – bewusst, und als breite Intervalle sichtbar.
  • Cross-User-Personalisierung: Bewusst ausgeschlossen (0 Tracker). Cold-Start-Hilfe über Ähnlichkeitsseeds wäre ein nächster Schritt.
  • Skalierung: Laplace + SQLite sind für Tausende, nicht Millionen Nutzer gedacht. Wechsel auf Postgres/Streaming-Inferenz ist der geplante Pfad.
